# 项目分析 SOP

版本：v1<br>
建立日期：2026-10-25<br>
适用对象：项目链接、合约地址、白皮书、旧调研、代币模型、收益策略、GitHub 仓库、产品截图、交易记录。

## 0. 这份文档解决什么问题

目标不是把项目介绍复述一遍，而是回答五个问题：

1. 它现在到底是什么，是否真的在运行？
2. 钱从哪里来，最终由谁支付？
3. 新参与者按当前条件进入，单位成本是多少？
4. 最坏情况下会损失什么，退出路径是否存在？
5. 哪些新证据会推翻当前判断？

最终必须给出明确判断：**可以做、只能小仓验证、只适合研究、或不应参与**。不能只罗列优缺点。

## 1. 启动规则

收到任何项目材料时，先判断材料类型，再选择验证路径：

| 材料 | 第一动作 | 不能直接相信的内容 |
|---|---|---|
| 项目链接 | 打开官网、文档、API、链上入口 | 首页宣传、倒计时、APY |
| 合约地址 | 确认链、区块、实现合约、源码匹配 | 浏览器标签名、代币名 |
| 白皮书/文档 | 提取机制、公式、权限、费用流 | “安全”“审计”“去中心化”等形容词 |
| 旧调研 | 建“旧结论 vs 当前事实”差异表 | 旧 TVL、旧公式、旧状态 |
| 收益截图 | 找交易哈希、仓位、时间窗口 | 截图 PnL、单日榜单 |
| GitHub 仓库 | 看代码、提交、测试、依赖、发布物 | README 功能清单 |
| 交易记录/钱包 | 区分已实现、未实现、转入转出 | 总资产、账面浮盈 |

### 必须记录

- 数据时间，精确到分钟和时区。
- 链 ID、区块高度，或 API 返回时间。
- 数据源 URL、接口名、查询参数。
- 金额单位、代币精度、是否为美元等值。
- 哪些是事实，哪些是推断，哪些仍未知。

### 证据等级

| 等级 | 来源 | 用法 |
|---|---|---|
| A | 链上状态、已验证源码、可复现 RPC 查询 | 可作为核心结论 |
| B | 官方文档、官方 API、正式公告 | 可作机制说明，仍需与 A 对照 |
| C | 第三方数据平台、浏览器索引 | 用于交叉验证 |
| D | 社区帖子、KOL、截图 | 只能作为线索 |
| E | 项目方口头承诺 | 不能作为已发生事实 |

结论的证据等级低于 B 时，必须写明“未验证”。

## 2. 第一层：身份与真实性

先确认“这是不是同一个项目”，再分析经济模型。

### 2.1 基本身份

- 官网域名、文档域名、X/GitHub/Discord 是否互相指向。
- 合约地址是否由官方文档、前端请求或正式公告共同确认。
- 部署链、部署者、部署时间、代理管理员。
- 代币与协议合约是否分离，是否存在多个版本。
- 当前前端调用的实现合约，是否就是白皮书描述的合约。

### 2.2 合约可信度

- 浏览器是否验证源码；Sourcify 或 Etherscan 是否有匹配。
- 代理合约的 implementation 是否可变。
- upgrade admin 是 EOA、multisig 还是 timelock。
- timelock 实际延迟、执行权限、guardian 权限。
- 是否暂停、冻结、黑名单、强制转移、修改费率等特权。
- 预言机、价格源、keeper、relayer 是否为中心化地址。
- 审计报告是否覆盖当前实现版本，而不是旧版本。

### 2.3 判断规则

- “有审计”不等于当前代码安全。
- “源码未匹配”不等于恶意，但意味着无法独立验证核心逻辑。
- “2-of-3 multisig”只说明需要三把钥匙中的两把，不说明持有人可信。
- “24 小时 timelock”只能降低突然升级风险，不能消除管理员作恶。

## 3. 第二层：当前运行状态

必须用实时数据回答，不能沿用旧报告。

### 3.1 通用快照

| 类别 | 必查项 |
|---|---|
| 时间 | 当前时间、数据时间、区块高度 |
| 规模 | TVL、活跃资金、闲置资金、借款、储备 |
| 用户 | 地址数、活跃地址、持仓集中度 |
| 交易 | 24h/累计成交量、成交笔数、未平仓量 |
| 费用 | 24h/累计费用、费用归属、未支付队列 |
| 代币 | 总供应、流通量、质押量、增发速度 |
| 状态 | 交易、充值、提现、领取、暂停开关 |
| 退出 | 可转让性、流动性、赎回规则、锁定期 |

### 3.2 状态字段不能只看名字

`tradingPaused=false` 不代表所有操作都正常；还要分别验证：

- 开仓是否成功。
- 平仓是否成功。
- 充值是否入账。
- 提现是否可发起、是否进入队列。
- 奖励是否可领取。
- 链上事件是否与前端显示一致。

### 3.3 TVL 拆解

至少拆成：

```text
TVL
├── 用户闲置余额
├── 持仓保证金
├── LP 可调用资金
├── 协议储备
└── 其他债权/负债
```

TVL 大不代表资金在承担风险，也不代表有真实收益。闲置余额占比高，说明资金效率低或用户在等待退出。

## 4. 第三层：机制重建

不要从项目分类开始，要从资金流开始。

### 4.1 画出现金流

用文字或表格写清：

```text
谁付款 -> 付给谁 -> 为什么付 -> 什么条件下付 -> 谁承担亏损
```

必须区分：

- 用户充值，不是收入。
- 用户交易亏损，不一定全部成为 LP 现金。
- 累计成交额，不是协议收入。
- 代币增发，不是现金流。
- 账面奖励，不等于已领取现金。
- 新用户本金，不是可持续收益。

### 4.2 找出真正的收益来源

逐项标记：

- 交易手续费。
- 买卖价差。
- 资金费/借贷利息。
- 清算罚金。
- 对手方亏损。
- 外部协议收益。
- 代币增发补贴。
- 新资金流入。

如果主要收益来自“后来者本金”或“代币价格上涨”，必须明确标注为**再融资型/庞氏风险**，不能称为真实收益。

### 4.3 识别关键公式

把白皮书里的公式改写成可计算形式，并检查：

- 输入单位是什么。
- 是否使用供应量、TVL、时间或价格。
- 是线性、分段线性还是指数。
- 边际值是多少，不是只看平均值。
- 公式何时升级过，旧报告是否仍适用。

## 5. 第四层：单位经济模型

这是整份分析的核心。所有项目最终都要落到“每单位成本”和“每单位净回收”。

### 5.1 统一口径

选择一个可比较的单位，例如：

- 每 10,000 枚代币的获取成本。
- 每 1,000 USDC 本金每日净收益。
- 每 1 个用户/订单/任务的毛利。
- 每 1 美元 TVL 的年化净费用。

### 5.2 成本必须包含

```text
总成本
= 直接亏损
+ 手续费
+ 滑点
+ 资金占用成本
+ 对冲成本
+ 桥接/提现费用
+ 失败交易和清算损失
```

### 5.3 收益必须打折

```text
可分配净收益
= 毛收益
- 协议抽成
- 领取成本
- 价格折扣
- 未实现部分
- 延迟支付风险
```

### 5.4 回本公式

```text
单位获取成本 = 总净成本 / 获得代币数量
日单位分配 = 24h 可分配费用 / 当前质押总量
静态回本天数 = 单位获取成本 / 日单位分配
```

必须同时给出敏感性表，至少改变三个变量：

- 费用下降 50%。
- 质押总量上升 50%。
- 代币增发/稀释 2 倍。

如果回本天数只在一个极窄条件下成立，结论应写“条件性回本”，不能写“年化 X%”。

### 5.5 代币估值规则

- 可转让 + 有深度 + 有真实成交：可以计算可执行市值。
- 可转让但流动性极差：只能给折价区间，不能按最后成交价。
- 不可转让：不计算市值和 FDV，只计算现金分红回收。
- 锁仓/线性释放：按可领取部分计算，不能把未来释放当现值。

### 5.6 份额制项目：算力、矿机、节点、NFT 分红

适用于 Computers RH 这类“购买设备获得算力，按全网算力份额分奖励池”的项目，也可用于节点质押、矿池、LP 激励和 NFT 产出。

**不能只看单机日收益，必须算份额。**

```text
用户每分钟产出 = 用户有效算力 / 全网有效算力 × 每分钟奖励预算
用户日产出 = 用户算力份额 × 当日奖励池释放量
算力份额 = 用户有效算力 / (用户有效算力 + 其他玩家有效算力)
```

关键变量：

| 变量 | 影响 |
|---|---|
| 全网算力 | 翻倍则同算力份额减半 |
| 奖励池余额 | 决定未来可分配总量 |
| 每日释放比例 | 当前 10%/天，会随池子余额下降而衰减 |
| 币价 | 同样代币产出折算的美元收入 |
| 电费 | 固定美元成本，币价下跌时相对更重 |
| 设备价格 | 决定初始成本 |
| 计数门槛 | 决定设备是否获得 boost |
| boost 上限 | 改变有效算力，但不改变全网竞争 |

**回本公式：**

```text
日净现金流 = 日代币产出 × 币价 × (1 - 卖出税) - 日电费
回本天数 = 初始投入 / 日净现金流
份额稀释后产出 = 原产出 × 原全网算力 / 新全网算力
```

**必须做三档情景：**

| 情景 | 全网算力 | 币价 | 用途 |
|---|---:|---:|---|
| 乐观 | 不变 | 不变或上涨 | 只用于上限参考 |
| 中性 | 2 倍 | 下跌 50% | 主要判断依据 |
| 悲观 | 5–10 倍 | 下跌 80% | 检查是否归零 |

只按当前算力和当前币价算出的“数小时回本”不能作为决策依据。份额制项目的收益会被新增算力持续稀释，设备买入后不能因为“已经回本 30%”就忽略后续电费。

**设备性价比的正确算法：**

```text
每 H/s 购置成本 = 设备价格 / 有效 H/s
每 H/s 日成本 = 日电费 / 有效 H/s
每 H/s 日毛收入 = 日代币产出 × 币价 / 有效 H/s
每 H/s 日净收入 = 每 H/s 日毛收入 - 每 H/s 日成本
```

不能只比较 `价格 / H/s`，因为高功耗设备的电费会吃掉产出；也不能只看 boost 后的名义算力，因为 boost 门槛会迫使你购买更贵设备。

**份额制项目的结构性风险：**

- 奖励池由新玩家消费注资，老玩家分红，属于再融资型现金流。
- 新增算力会稀释老玩家份额，早期高收益不可持续。
- 币价上涨只能短期改善美元回本，不能改变算力竞争。
- 币价下跌时，电费是刚性美元支出，可能从盈利变成持续亏损。
- 设备不可退款、不可转移或流动性差时，退出价值接近零。
- 官方前端、合约、代币地址必须交叉验证，假币和钓鱼链接常见。

**判断规则：**

1. 先算当前全网算力下的份额，不用宣传中的“单机日收益”。
2. 再算全网算力翻 2 倍、5 倍后的份额和回本。
3. 把电费、买卖税、滑点、领取门槛全部计入。
4. 如果中性情景下回本超过可接受期限，结论只能是“小仓验证”或“不参与”。
5. 如果收益主要来自新玩家购买设备，而不是外部收入，必须标注“再融资依赖”。

## 6. 第五层：案例拆解

案例的作用是检验机制，不是挑选最漂亮的成功故事。

### 6.1 至少选三类

| 类型 | 目的 |
|---|---|
| 早期低成本账户 | 看先发优势是否真实、是否已回本 |
| 晚期高换手账户 | 看当前边际成本下能否持续 |
| 方向性盈利案例 | 区分“策略收益”和“机制补贴” |

可选补充：

- 最大亏损账户。
- 最大持仓账户。
- 新进入账户。
- 已退出账户。
- 团队/关联地址。

### 6.2 每个案例必须写

- 地址或可验证标识。
- 数据时间窗口。
- 已实现 PnL、未实现 PnL 分开。
- 获得代币数量与成本。
- 累计奖励、已领取、未领取分开。
- 奖励覆盖亏损比例。
- 单位成本，例如 `USDC / 10,000 枚`。
- 当前仓位、保证金、名义额。
- 该案例能证明什么，不能证明什么。

### 6.3 案例计算

```text
奖励覆盖率 = 累计已领取奖励 / |累计已实现亏损|
每万枚成本 = |累计已实现亏损| / 持有代币数量 × 10,000
剩余回本天数 = 尚未回收成本 / 当前每日分配
盈利保留率 = 净盈利 / 毛盈利
```

### 6.4 防止误读

- 单日榜单盈利不能代表累计盈利。
- 高成交量不能代表高收益。
- 单个地址不能代表全部用户。
- 排行榜聚合数据不是完整账本。
- 早期账户的低成本不可复制。
- 方向性交易的高收益来自杠杆和判断，不是机制套利。
- 87.5% 这类比例若没有完整成交明细，不能写成固定常数。

## 7. 第六层：风险与反证

### 7.1 风险清单

| 风险 | 要问的问题 |
|---|---|
| 合约 | 是否可升级、是否有特权、源码是否匹配 |
| 经济 | 收益是否依赖新资金、是否存在期限错配 |
| 流动性 | 能否退出、退出是否排队、深度多少 |
| 预言机 | 价格源是谁、是否可操纵、异常时如何处理 |
| 清算 | 硬清算阈值、保险基金、坏账归属 |
| 治理 | 多签是谁、timelock 多长、紧急权限 |
| 对手方 | LP、做市商、托管方、relayer 是否可信 |
| 监管 | 代币是否证券、地区限制、KYC/AML |
| 操作 | 私钥、授权、桥、钓鱼、前端劫持 |
| 数据 | API 是否自报、索引是否完整、口径是否变化 |

### 7.2 必须写“什么会改变判断”

至少列 3 条增强证据和 3 条削弱证据：

**增强判断**

- 核心合约源码匹配且审计覆盖当前版本。
- 真实费用连续 30 天覆盖成本。
- 代币开放转让并形成可持续深度。
- 队列长期为空，提现正常。
- 新增资金没有推高单位成本。

**削弱判断**

- 单位成本继续指数上升。
- 费用主要来自少数关联地址。
- 质押分母快速上升，单位分配下降。
- 提现开始排队或延迟。
- 代币仍不可转让且没有分红。
- 实现合约升级且无源码/审计。

### 7.3 结论分级

| 等级 | 条件 | 建议 |
|---|---|---|
| 绿 | 机制、数据、退出、合约均可验证，单位经济在保守假设下成立 | 可正常参与，仍需限额 |
| 黄 | 机制成立但关键条件未验证，或收益依赖持续费用 | 只小仓验证 |
| 橙 | 单位经济明显恶化、流动性不足、合约不透明 | 只研究，不投入 |
| 红 | 核心宣传被证伪、收益依赖新资金、无法退出 | 不参与 |

## 8. 第七层：可复现性

报告必须能被另一个人复算。

### 8.1 快照目录

建议每次分析建立：

```text
项目名_snapshot_YYYY-MM-DD/
├── meta.json          # 时间、链、区块、数据源
├── protocol.json      # TVL、供应、费用、队列
├── contracts.json     # 地址、实现、源码匹配、权限
├── cases.csv          # 案例地址与指标
├── history.json       # 历史序列
└── notes.md           # 异常、超时、口径变化
```

### 8.2 报告中必须附

- 数据接口或 RPC 方法。
- 查询参数和时间范围。
- 关键公式及代入值。
- 舍入规则。
- 未取得的数据。
- 已尝试但失败的验证。

### 8.3 不可省略的声明

```text
本文没有连接钱包、没有签名、没有提交交易。
所有金额按 1 USDC = 1 美元处理。
模型结果为条件推演，不代表已实现收益。
```

## 七、风险

## 10. 快速执行顺序

时间有限时，按以下顺序做，不要从写背景开始：

1. 确认官网、文档、合约、链。
2. 拉当前 TVL、供应、费用、队列、状态。
3. 找到收益公式和资金流。
4. 算当前边际成本，不算历史平均成本。
5. 找一个早期账户、一个晚期账户、一个盈利交易。
6. 找退出路径和合约权限。
7. 写“什么会推翻判断”。
8. 最后写结论和建议。

## 11. 常见错误

| 错误 | 正确做法 |
|---|---|
| 把 TVL 当安全垫 | 拆成闲置、保证金、LP、储备 |
| 把成交量当收入 | 找手续费和净现金流 |
| 把累计费用当协议收入 | 确认费用归属和分配链路 |
| 把负 PnL 全算成 LP 利润 | 区分对手方盈利、费用、未实现头寸 |
| 用旧公式算新供应 | 先确认合约版本和公式是否升级 |
| 用最后成交价给不可转让代币估值 | 只算现金分红 |
| 用单日榜单证明策略有效 | 看累计已实现和完整周期 |
| 把审计当安全保证 | 核对审计版本、范围和权限 |
| 把多签当去中心化 | 查持有人、阈值、timelock |
| 只写优点 | 必须写反证条件和退出风险 |

## 12. 案例校准一：Papertrade

这个案例展示了 SOP 如何改变结论：

1. 旧报告认为发行约为 `100 PAPER / 1 USDC` 亏损。
2. 链上复核发现合约升级后改为指数增发，当前边际约 `9.9 PAPER / 1 USDC`。
3. 同样两腿对冲，单位成本从约 `15.69` 升到 `158.40 USDC / 万枚`。
4. 代币不可转让，因此不能用市值证明回本，只能按分红计算。
5. 早期钱包成本约 `85.56`，晚期钱包约 `159.53`，说明先发优势真实但不可复制。
6. 最终判断从“低成本套利”改为“用亏损买长期分红期权，只适合小仓验证”。

核心不是 Papertrade 本身，而是这套顺序：**先验证，再建模；先算边际，再看案例；先找退出，再谈收益。**

## 13. 案例校准二：Computers RH

这个案例展示了**份额制挖矿**项目如何被错误地按“固定收益”理解。

### 13.1 文章中的原始模型

| 参数 | 文章口径 |
|---|---:|
| 消费分配 | 60% 奖励池 / 20% 销毁 / 20% 国库 |
| 奖励释放 | 每天释放池内 10%，按分钟分配 |
| 领取门槛 | 岛屿累计支出 25 美元 |
| 电费 | 0.55 美元/kWh |
| 交易税 | 买入 3% / 卖出 3% |
| 份额公式 | 用户 H/s ÷ 全网 H/s × 每分钟预算 |

文章把设备写成美元锚定价，代币价格只影响产出折算，不改变设备标价。这个描述本身合理，但**不能推出“回本时间固定”**，因为全网算力会持续上升。

### 13.2 正确的计算顺序

```text
第一步：设备有效算力 / 当前全网算力 = 当前份额
第二步：当前份额 × 每日释放量 = 当前日代币产出
第三步：日代币产出 × 币价 × 0.97 - 日电费 = 日净现金流
第四步：初始投入 / 日净现金流 = 当前条件下回本天数
第五步：把全网算力改为 2 倍、5 倍、10 倍，重新计算
```

只做前四步会得到“数小时或数天回本”的幻觉；第五步才决定这个项目能不能参与。

### 13.3 文章里最容易被误读的数字

| 原文数字 | 容易得出的错误结论 | 正确理解 |
|---|---|---|
| 25 美元 Seed 日毛收益 89 美元 | 7 小时回本 | 只在当前算力和币价不变时成立 |
| Grove 实测 7 小时产出下降 55% | 只是短期波动 | 这是份额被新增算力稀释的直接证据 |
| 币价翻倍“救回稀释” | 项目仍然赚钱 | 只是美元计价暂时改善，算力竞争仍在继续 |
| 各档设备回本接近 | 买最贵的最划算 | 高价设备的前置门槛和电费风险更高 |
| boost 上限 84% | 必须堆满 boost | boost 只放大个人份额，不改变全网竞争 |
| 现实回本 = 理想 × 3–5 倍 | 可以按这个区间下注 | 稀释可能超过 5 倍，币价也可能继续下跌 |

### 13.4 关键结构判断

文章已经指出“池子由玩家注资，后人养前人”，这是最重要的结论，应该放在分析开头，而不是坑点清单第 10 条。

原因是：

- 设备销售款中 60% 进入奖励池，构成后续玩家的产出。
- 新玩家购买设备会增加全网算力，同时稀释老玩家份额。
- 如果没有外部真实收入，奖励池本质上是新资金的再分配。
- 币价上涨可以延缓崩盘，但不能改变资金结构。

因此这个项目的准确定性是：**高摩擦、强稀释、再融资依赖的份额制 GameFi**，不是“买机器收租”。

### 13.5 必须补做的验证

文章发布于 2026-10-09，早于公开 launch，不能直接作为当前事实。使用前必须重新核对：

- Robinhood Chain 的 chain ID、RPC、浏览器和当前区块。
- CRH 官方合约地址，是否与官推一致。
- 游戏合约是否验证源码，升级权限和提款权限归谁。
- 当前全网算力、奖励池余额、每日实际释放量。
- 当前币价、池子深度、买卖 3% 税之外的实际滑点。
- 设备价格是否仍为美元锚定，是否已调整。
- 电费、维修、过热规则是否与文章一致。
- 领取门槛是否仍为 25 美元，领取是否即时。
- 当前是否已开放提现，是否存在排队或限额。

这些项目未验证前，文章只能作为机制说明，不能作为收益依据。

### 13.6 本案例的判断模板

```text
项目类型：份额制 GameFi 挖矿
真实收入来源：设备销售款进入奖励池，主要是新资金再分配
当前边际收益：待用实时全网算力和币价计算
主要风险：算力稀释、币价下跌、电费刚性、设备不可退、合约权限
结论等级：橙色（只研究）或黄色（仅小仓验证）
升级为绿色的条件：外部收入占比可验证、合约源码匹配、退出正常、中性情景回本可接受
```

**一句话：Computers RH 的机器不是“矿机资产”，而是一张持续消耗电费、份额不断被稀释的奖励池门票。**
